# Repo Catalog Operator

## Mission

Maintain a searchable GitHub repository catalog whose single human-maintained
source is `scripts/curated.json`. All generated files must be produced by the
repository scripts. The operator must leave the catalog valid, internally
consistent, and safe for the public repository.

This is an execution standard, not a suggestion list. Follow the operation
order below and stop at the first failed gate.

## Non-Negotiable Rules

1. Never write private repository data to `scripts/curated.json`,
   `data/repos.json`, or `categories/`.
2. Never edit `data/repos.json`, `categories/*.md`, or
   `data/review-needed.json` by hand. Regenerate them.
3. Never use a short repository name as an identity. The identity is the
   normalized, case-insensitive `owner/name` pair. A short name may remain as
   a storage key only for a legacy or non-conflicting entry; it must never be
   used for duplicate detection or owner resolution.
4. Re-adding the same repository is a no-op. A same-name repository owned by a
   different owner is a separate project and must be retained using qualified
   keys.
5. Never silently repair an invalid category, lifecycle value, argument, or
   input path. Fail before writing output.
6. Star discovery is additive. Do not delete an entry because the user later
   unstars it.
7. Do not commit or push unless the user explicitly asks for publication.
8. Do not claim success unless the final validation and tests pass.
9. Never use force-push, `git reset --hard`, or `git checkout --` to resolve
   this repository's changes.

## Source And Generated Files

| Role | File | Rule |
|---|---|---|
| Human source | `scripts/curated.json` | Add descriptions, keywords, category, lifecycle, and repository identity here. |
| Public generated data | `data/repos.json` | Generated with `--public`; must contain no private records. |
| Category output | `categories/*.md` | Generated from the same public data. |
| Audit output | `data/review-needed.json` | Generated by `audit.py`; do not hand-edit. |
| Local private source | `scripts/curated.private.json` | Gitignored; local-only and never merged in public mode. |
| Local full output | `/tmp/repo-catalog-full.md` | Generated by `build_full_md.py`; may include private records. |
| Standard procedure | `.agents/skills/repo-catalog-operator/SKILL.md` | This document; update it when the workflow contract changes. |

## Curated Entry Contract

Every new entry must have these human fields:

```json
{
  "category": "one allowed category key",
  "cn": "concise Chinese function description",
  "keywords": ["search keyword"],
  "status": "unreviewed",
  "priority": "unclassified",
  "lastReviewedAt": "",
  "duplicateGroup": "",
  "alternatives": [],
  "replacement": "",
  "isFork": false
}
```

External entries must also carry `external: true`, `owner`, and the canonical
GitHub `url`. GitHub metadata such as language, stars, forks, license, topics,
updated date, archive state, and disabled state is refreshed by
`refresh_external_repos.py`.

Allowed lifecycle values:

- `status`: `unreviewed`, `active`, `watch`, `archived`, `obsolete`,
  `replaced`
- `priority`: `unclassified`, `primary`, `alternative`, `reference`

New or automatically discovered entries always start as `unreviewed` and
`unclassified`. Do not infer `primary` from star count.

## Category Decision Table

Choose exactly one existing key. Do not invent a new key during repository
addition.

| Key | Use for |
|---|---|
| `ai-llm-models` | Models, fine-tuning, local model training, model deployment |
| `ai-llm-prompts` | Prompt collections, jailbreaks, prompt techniques |
| `ai-llm-agents` | Agents, agent frameworks, tool calling, browser agents, agent benchmarks, workflows |
| `ai-llm-api` | AI APIs, gateways, compatible proxies, self-hosted AI UIs |
| `ai-llm-tutorials` | LLM tutorials, courses, source explanations, learning resources |
| `network-proxy` | Proxies, subscriptions, Cloudflare, VPS networking |
| `media` | Video, image generation, media processing, music |
| `content-writing` | Writing, public-account formatting, social content, content operations |
| `dev-data-tools` | Developer tools, security tools, APIs, datasets, knowledge graphs, local services |
| `knowledge-books` | Books, reading lists, corpora, general knowledge collections |
| `personal-projects` | Personal or private self-built projects |

Classification must be based on the repository's README and implementation
purpose, not its name or star count. Record the reason in the final response.

If a repository does not fit an existing key, stop and propose a category
change. Adding a category requires updating the category definitions,
`categories/`, generators, validator, audit/recommendation assumptions, and
regression tests together; never invent a category in `curated.json` alone.

## Standard Operations

### 0. Preflight

Run from the repository root:

```bash
git status --short --branch
```

If the worktree is clean and the operation will publish changes, synchronize
without overwriting local work:

```bash
git pull --ff-only origin main
```

Do not pull or rebase over uncommitted user changes without inspecting them.

### 1. Inspect A GitHub Repository

For a URL or `owner/name`, inspect the README and GitHub metadata before
classifying it. For web content, use the available repository reader and keep
the source URL. Capture only facts needed for the catalog:

- purpose and primary workflow
- implementation type and major technologies
- public/private, fork, archived, or disabled state
- license and any split license for datasets or task suites
- a concise Chinese description
- search keywords

Do not copy a README wholesale into `cn`. Do not invent metrics or features.

### 2. Add One Repository

Use the existing writer. Pass an explicit category, Chinese description, and
comma-separated keywords:

```bash
python3 scripts/add_repo.py \
  "https://github.com/OWNER/REPO" \
  --cn "中文功能说明" \
  --kw "关键词1,关键词2,关键词3" \
  --cat "category-key"
```

Expected behavior:

- same normalized `owner/name`: report already present and make no duplicate
- same short name but different owner: migrate the old short key to its
  qualified identity and retain both projects
- private repository: reject before public output is written
- invalid category: reject before the GitHub API call

After a successful add, run the full synchronization operation in section 5.

### 3. Discover Starred Repositories

Starred third-party repositories are not returned by
`/users/skychen2/repos`. Use the authenticated Star collector:

```bash
python3 scripts/fetch_starred_repos.py --dry-run
```

Treat the dry-run as a preview gate. Record the discovered, added, updated,
migrated, and owned-repository counts before writing. If the user's request is for one newly starred project, identify its exact
`owner/name` from the Star list with:

```bash
gh api user/starred -X GET -f sort=created -f direction=desc -f per_page=20 \
  --jq '.[].full_name'
```

Then use section 2 for that exact repository; do not run the full write command
for a one-project request.

To write all newly recognized third-party Stars:

```bash
python3 scripts/fetch_starred_repos.py
```

Authentication resolution is:

1. `STARRED_REPOS_TOKEN`
2. `GH_TOKEN`
3. `GITHUB_TOKEN`
4. local `gh auth token`

CI must provide `STARRED_REPOS_TOKEN` with permission to read the user's
starred repositories. A missing or unauthorized token is an error, not an
empty Star list.

If only one newly starred project should be added, identify its exact
`owner/name` from the Star list and use section 2. Do not turn a one-project
request into an unapproved historical batch import.

Automatically discovered entries use conservative defaults and must later be
reviewed manually. They are still subject to the same generation, audit, and
validation gates.

### 4. Refresh External Metadata

Refresh only after `curated.json` has been updated:

```bash
python3 scripts/refresh_external_repos.py
```

Rules:

- API success updates automatic fields only.
- API failure returns non-zero and preserves the last successful metadata.
- inaccessible repositories remain as entries with `missing` and
  `checkError` markers.
- human fields must not be overwritten.
- `--dry-run` must not write `curated.json`.

### 5. Full Synchronization

Run these commands in this exact order. Use one command per step so the
failure point is visible:

```bash
python3 scripts/fetch_public_repos.py /tmp/repos.json
```

```bash
python3 scripts/refresh_external_repos.py
```

```bash
python3 scripts/generate.py --public /tmp/repos.json
```

```bash
python3 scripts/audit.py
```

```bash
python3 scripts/validate.py
```

```bash
python3 -m unittest discover -s tests -v
```

```bash
python3 -m py_compile scripts/*.py tests/*.py
git diff --check
```

Success requires all commands to exit zero. The expected generated invariant
is:

```text
len(data/repos.json) == len(scripts/curated.json)
```

For a local index that may include private records, run separately:

```bash
python3 scripts/build_full_md.py
```

Never use the local full output as the public artifact.

### 6. Recommendation Queries

Use the recommender only against generated data:

```bash
python3 scripts/recommend.py "功能需求" --top 3
```

Reject blank queries and non-positive `--top`. Alternatives must exclude
`archived`, `obsolete`, `replaced`, and `missing` entries. If no meaningful
match reaches the minimum score, report no result instead of guessing.

### 7. Publish

Publication is a separate explicit operation. Before it, inspect the diff:

```bash
git status --short --branch
git diff --stat
git diff --check
```

Classify every changed file as part of the requested operation or unrelated
user work. If unrelated changes are present, stop and ask before staging, or
stage only the intended paths. Do not blindly use `git add -A` when the
worktree contains unrelated changes.

Then publish:

```bash
git add -A
git commit -m "add repo: OWNER/REPO"
git push origin main
```

If push is rejected because remote `main` advanced:

```bash
git fetch origin
git rebase origin/main
```

Resolve conflicts by preserving both valid changes. Regenerate generated files
with section 5 after resolving source conflicts. Continue the rebase, rerun
all validation, and push normally. Never force-push.

## Failure Gates

Stop and report the exact failed gate when any of these occurs:

- GitHub API, network, authentication, or rate-limit failure
- invalid argument, category, lifecycle value, or JSON
- private repository detected for public output
- generated count or category file mismatch
- audit or validation error
- test, compile, or whitespace check failure
- non-fast-forward push or unresolved rebase conflict

Do not generate a reassuring summary after a failed gate. Do not commit stale
or partially refreshed metadata.

## User-Facing Completion Format

Use this compact report after an operation:

```text
操作：新增 / Star 发现 / 刷新 / 生成 / 审计 / 发布
项目：owner/name
分类：category-key
结果：成功 / 未写入 / 已写入但未发布
目录规模：N 个项目，M 个外部收藏
验证：测试、编译、validate、diff check 的结果
提交：未提交 / commit-id，远程是否同步
备注：仅列出真实警告、待人工审核项或失败原因
```

Never report a generated or pushed result unless the corresponding command
actually completed successfully.
